Pitch File 04 — Deployment, Edge & Scaling

Q1: What is the deployment architecture for the system?
A: The system uses a split deployment across two cloud providers. The frontend is a Next.js 16.3.1 application deployed on Vercel, leveraging Turbopack for fast builds and React 19 for the UI layer. The backend is a FastAPI 0.141 application running Python 3.12 on Render, serving the ML inference API and WebSocket connections. MapLibre GL provides map visualization with no API key requirement, and Open-Meteo supplies weather data without authentication. This separation allows the frontend team to iterate independently from the backend ML pipeline while keeping deployment costs minimal.

Q2: Why was ONNX Runtime chosen over TFLite for edge deployment?
A: ONNX Runtime was selected because it runs faster on ARM CPUs like those found in Raspberry Pi and Jetson devices, which is where the edge inference will execute at mine sites. A single ONNX format covers all three model types in the system — XGBoost, LSTM, and CNN-LSTM — whereas TFLite would require different conversion pipelines per model family. ONNX Runtime also provides better operator coverage for the feature transformations used in the 10-feature pipeline. The one-format-fits-all approach simplifies the build artifact and reduces the surface area for conversion errors during model export.

Q3: How does edge deployment work at remote mine sites without internet connectivity?
A: The architecture follows a sensor-to-edge-to-cloud path where sensors feed data into an edge device (Raspberry Pi or Jetson), which runs local ONNX inference and triggers local alerts — a siren, GPIO pin, or GSM SMS — without any internet dependency. Cloud dashboard sync happens opportunistically when connectivity is available, but the critical safety loop never depends on it. The standalone Python script for offline mode makes zero network calls and was demonstrated running with WiFi disabled next to the normal dashboard to prove this invariant. This design is essential for remote mine sites where network outages are common and life-safety decisions cannot wait for a cloud round-trip.

Q4: What are the hardware requirements for Raspberry Pi or Jetson devices running ONNX inference?
A: A Raspberry Pi 4 with 4GB RAM is sufficient to run ONNX models for the 10-feature input pipeline, as the model file sizes are small — RF and XGB models exported via joblib compress to under a few MB. The Jetson Nano or Orin Nano provides GPU acceleration for the CNN-LSTM model if real-time inference on the LSTM component becomes a bottleneck. Both devices support GPIO for direct siren/relay control and have UART interfaces for GSM modules. Power consumption is low enough to run on solar-charged battery systems common at remote mining operations.

Q5: How does the system achieve sub-minute alert latency?
A: The target sub-minute latency is achieved by eliminating unnecessary network hops in the critical alert path. Sensor data is ingested directly by the edge device, ONNX inference completes in milliseconds for tabular models, and the alert trigger fires immediately when risk_level crosses into warning or evacuation. On the cloud side, FastAPI pushes AlertEvent objects over WebSocket to the dashboard, bypassing polling entirely. The 16-zone grid refresh cycle is designed to process new readings as they arrive, and the risk classification runs on every ingestion batch rather than on a fixed schedule.

Q6: What is the Twilio SMS integration plan and current status?
A: Twilio SMS is planned as a secondary alert channel to complement edge-based siren and GPIO alerts, providing remote notification to site managers who may not be physically present. The AlertEvent schema already carries the risk_level and zone metadata needed to compose an SMS payload. The integration has not been built yet because budget allocation and API key provisioning are still pending. Once keys are available, the implementation is straightforward — a POST to the Twilio REST API triggered by the same alert evaluation logic that drives WebSocket emissions.

Q7: How does the system scale to other mine sites?
A: The zone grid is parameterized through an AOI bounding box stored in data/aoi.json, so deploying to a new mine requires only a new bounding box and a re-run of the GEE satellite data pipeline. The 10-feature SensorReading schema is mine-agnostic — temperature, humidity, vibration, gas ppm, wind speed, and other fields are defined by the sensor spec, not by the site. The ML models are trained on generalized patterns (rainfall intensity, vibration frequency, gas concentration thresholds) rather than site-specific historical data. Adding a new mine is a configuration change, not a code change.

Q8: How will real sensor feeds replace the synthetic data generator?
A: The synthetic data generator currently produces SensorReading objects that conform to the same schema the live ingestion pipeline will consume, making the swap a drop-in replacement. Real sensors would push readings via MQTT or HTTP POST to the same FastAPI endpoint that the generator targets. The feature extraction pipeline — rolling windows, lag features, and the 10-feature column order defined in feature_order.json — operates identically on synthetic or real data. This is by design: the synthetic generator was built to mirror the exact shape of live sensor output so that model performance degrades zero when switching sources.

Q9: What is the regional early warning network concept?
A: Multiple mine sites could share trained models through a federated learning approach where each site contributes gradient updates without exporting raw sensor data. This preserves data sovereignty while improving model generalization across geological and climatic conditions. The 16-zone grid structure at each site maps to a common spatial representation, enabling cross-site risk correlation — for example, detecting a regional weather system that affects multiple mines simultaneously. The cloud dashboard already supports multi-zone visualization, so extending it to multi-site is a matter of adding data sources, not rearchitecting the frontend.

Q10: How are model artifacts managed for deployment?
A: Models are saved in joblib format with dated filenames — rf-v2-20260820.joblib and xgb-v2-20260820.joblib — providing version traceability. The feature order is stored separately in feature_order.json, which defines the exact 10-feature column sequence the models expect at inference time. Label encoding is captured in label_encoding.json mapping numeric outputs to semantic risk levels: {0: safe, 1: warning, 2: evacuation}. ONNX export is planned for the edge deployment phase so that the same trained weights can run on both cloud (Python joblib) and edge (ONNX Runtime) without retraining.

Q11: Why was deployment started on Day 4-6 instead of Day 7?
A: Starting deployment early while there was schedule slack allowed environment configuration issues — Vercel build settings, Render Python version selection, and WebSocket proxy configuration — to surface and be resolved without compressing the final days. The FastAPI backend on Render required specific uvicorn configuration for WebSocket keepalive, and the Next.js 16.3.1 frontend needed Turbopack build flags that took iteration to get right. Catching these issues early meant that Day 7-8 could focus on edge ONNX export and integration testing rather than firefighting deployment failures. This is a standard practice for competition timelines where deployment surprises are high-probability risks.

Q12: How do local siren and GPIO alerts work in offline edge mode?
A: The edge device runs a standalone Python script that evaluates ONNX model output locally and triggers GPIO pins connected to relays, sirens, or strobe lights when risk_level reaches warning or evacuation thresholds. A GSM module (SIM800L or similar) can send SMS alerts via cellular network, which does not require internet — only cellular signal, which is more available at remote sites than broadband. The GPIO trigger logic is evaluated in-process with no external service dependency, so the alert fires within milliseconds of inference completion. This makes the safety system resilient to the same network failures that would disable a cloud-only approach.

Q13: How does the cloud dashboard sync when connectivity returns after an offline period?
A: The edge device buffers sensor readings and inference results locally during disconnection, then pushes the accumulated data to the FastAPI backend when connectivity is restored. The dashboard receives the backfilled data via WebSocket and renders it with appropriate time-gap indicators so operators can see what happened during the outage. The SensorReading schema includes timestamps that preserve the original ingestion time, not the sync time, so the historical record remains accurate. This opportunistic sync model means the cloud dashboard eventually converges with the edge state without requiring real-time connectivity.

Q14: Can the zone grid expand beyond the current 16-zone resolution?
A: The 16-zone grid (4x4) is a starting scale chosen to balance spatial resolution with computational cost and satellite tile availability from Google Earth Engine. The zone generation logic is parameterized — the grid dimensions are derived from the AOI bounding box in aoi.json, so increasing to 64 zones (8x8) or 256 zones (16x16) requires changing a single grid resolution parameter. Finer resolution improves spatial precision for alerting — identifying which specific area of a mine is at risk rather than which quadrant — but increases the number of models or inference calls needed. The ML pipeline processes zones independently, so scaling out is embarrassingly parallel.

Q15: How does the end-to-end integration test work from generator to dashboard?
A: The integration test starts the synthetic data generator producing SensorReading objects, feeds them into the FastAPI backend, triggers ML model inference (RF/XGB), evaluates risk classification, emits AlertEvent objects over WebSocket, and verifies the dashboard renders the updated risk state. This full path exercises every component in the stack — data generation, feature extraction, model prediction, risk logic, WebSocket transport, and frontend rendering — in a single automated sequence. The test was designed to be runnable in the competition demo environment to prove the system works end-to-end under judge observation. Catching integration breaks early during Day 4-6 deployment allowed these seams to be fixed while schedule slack still existed.
