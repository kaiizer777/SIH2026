Pitch File 04 — Deployment, Edge & Scaling

Q1: What is the deployment architecture for the system?
A:
- Split deployment: Next.js 16 frontend on Vercel and FastAPI backend on Render.
- MapLibre GL powers 3D maps without API keys, and Open-Meteo supplies free weather feeds.
- Turbopack powers instant frontend builds, and React 19 handles smooth UI updates.
- Enables the frontend and ML engineering pipelines to iterate and deploy independently.

Q2: Why was ONNX Runtime chosen over TFLite for edge deployment?
A:
- ONNX Runtime executes significantly faster on ARM CPUs used in Raspberry Pi and Jetson.
- A single ONNX standard covers all model families: RandomForest, XGBoost, GRU, and CNN-LSTM.
- Provides comprehensive operator support for 10-feature vector transformations on edge hardware.
- Eliminates fragmented multi-framework conversion pipelines, reducing edge deployment bugs.

Q3: How does edge deployment work at remote mine sites without internet connectivity?
A:
- Sensors feed directly into an on-site edge device running local ONNX inference.
- Triggers physical sirens, flashing lights, and GSM SMS directly over GPIO/UART pins.
- Safety-critical evacuation loops operate 100% locally with zero internet dependency.
- Cloud dashboards synchronize data opportunistically whenever network connectivity is restored.

Q4: What are the hardware requirements for Raspberry Pi or Jetson devices running ONNX inference?
A:
- Raspberry Pi 4 (4GB RAM) easily runs tabular tree models with small megabyte-scale footprints.
- NVIDIA Jetson Nano / Orin Nano adds GPU acceleration for deep learning sequence models.
- Low power draw allows devices to run on standard mine solar-battery backup systems.
- Features native GPIO and serial interfaces for direct industrial siren and relay integration.

Q5: How does the system achieve sub-minute alert latency?
A:
- Eliminates cloud network round-trips by running real-time ONNX inference directly at the edge.
- Tabular inference executes in milliseconds, triggering GPIO alarm relays immediately upon threshold crossing.
- Cloud telemetry streams over persistent WebSockets, bypassing slow HTTP polling delays.
- Refreshes risk classifications on every incoming sensor reading rather than on fixed schedules.

Q6: What is the Twilio SMS integration plan and current status?
A:
- Serves as a secondary remote alert channel for off-site managers and safety inspectors.
- The AlertEvent schema already formats the zone ID, severity, and timestamp into SMS payloads.
- Architecture is fully prepared to POST to Twilio APIs upon cloud alert trigger events.
- Provides redundant off-site notification without replacing primary on-site edge siren relays.

Q7: How does the system scale to other mine sites?
A:
- Parameterized through a simple geographic bounding box in aoi.json for any mine.
- The 10-feature schema is universally mine-agnostic across geology, weather, and sensors.
- Satellite pipelines automatically pull Copernicus DEM and Sentinel-1 SAR for new locations.
- Onboarding a new mine is a fast configuration change, not a software rewrite.

Q8: How will real sensor feeds replace the synthetic data generator?
A:
- The synthetic generator was strictly engineered to mirror production SensorReading Pydantic schemas.
- Real physical IoT sensors push data via MQTT or HTTP POST to identical backend routes.
- The feature extraction pipeline and feature_order.json column sequence operate completely unchanged.
- Guarantees zero code refactoring when transitioning from synthetic validation to live hardware.

Q9: What is the regional early warning network concept?
A:
- Enables multiple neighboring mines to share federated model improvements without exposing raw data.
- Standardized 16-zone spatial representations allow cross-mine correlation of regional storms.
- Protects commercial data privacy while boosting AI robustness across different geological formations.
- The dashboard easily expands to multi-mine views by adding new geographic data feeds.

Q10: How are model artifacts managed for deployment?
A:
- Serialized in joblib format with dated names (e.g. rf-v2-20260820.joblib) for strict version traceability.
- feature_order.json locks the exact 10-column feature sequence required for matrix inference.
- label_encoding.json defines unambiguous integer-to-string mappings: {0: safe, 1: warning, 2: evacuation}.
- ONNX exports ensure identical weight representations across cloud servers and edge microcontrollers.

Q11: Why was deployment started on Day 4-6 instead of Day 7?
A:
- Surfaced environment and build configuration issues early while schedule slack still existed.
- Resolved FastAPI WebSocket keepalive configs on Render and Turbopack flags on Vercel.
- Prevented last-minute integration panic, leaving Days 7-8 open for thorough end-to-end testing.
- Follows disciplined competition engineering practices to eliminate high-risk deployment surprises.

Q12: How do local siren and GPIO alerts work in offline edge mode?
A:
- Standalone Python edge scripts evaluate model predictions and trip hardware relays via GPIO.
- Activates physical alarms and high-decibel sirens in milliseconds with zero cloud dependencies.
- SIM800L GSM cellular modules send SMS alerts directly over voice/text cell networks.
- Ensures life-saving evacuation warnings fire even during complete power or fiber-optic outages.

Q13: How does the cloud dashboard sync when connectivity returns after an offline period?
A:
- The edge device buffers sensor logs and risk predictions locally on internal storage.
- Automatically pushes cached batches to the FastAPI backend once internet connectivity reconnects.
- Original sensor timestamps are strictly preserved, preventing historical logging distortions.
- The dashboard smoothly backfills offline intervals, maintaining an auditable safety record.

Q14: Can the zone grid expand beyond the current 16-zone resolution?
A:
- The 4x4 grid resolution is fully configurable via the bounding box in aoi.json.
- Easily scales to 64 zones (8x8) or 256 zones (16x16) by updating a single parameter.
- Higher resolution pinpoints micro-instabilities on specific bench faces rather than mine quadrants.
- Zones process independently in parallel, making spatial scaling computationally efficient.

Q15: How does the end-to-end integration test work from generator to dashboard?
A:
- Exercises the entire stack: sensor generation, feature assembly, ML inference, and WebSocket broadcast.
- Verifies that danger escalation instantly triggers AlertEvents and updates the 3D dashboard.
- Automated tests run end-to-end to provide undeniable live demonstration proof to judges.
- Validates that all decoupled microservices function cohesively under live operating conditions.
