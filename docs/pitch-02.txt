Pitch File 02 — Technical Architecture

Q1: Describe the end-to-end data flow from physical sensors to worker-facing alerts.
A: The pipeline ingests from four parallel streams: geotechnical sensors (displacement, vibration, pore pressure, strain), Sentinel-1 SAR backscatter (VV/VH), Copernicus GLO-30 DEM terrain derivatives (slope, aspect, curvature), and Open-Meteo rainfall. These converge at the FastAPI ingestion layer, which serializes each reading through the frozen Pydantic `SensorReading` schema defined in `backend/app/schemas.py`. The ML inference engine then computes a 10-feature vector per zone per timestep and produces a `RiskPrediction` with risk_level (safe/warning/evacuation) and risk_score (0–1). The result is pushed over a persistent WebSocket `/ws/feed` connection to the Next.js 16 dashboard, where MapLibre renders a 3D pit heatmap colored by risk level in real time. If the risk_level escalates to evacuation, the `AlertEvent` schema fires a structured alert with alert_id, zone_id, severity, and triggered_at timestamp — ready for downstream SMS or siren dispatch. The entire round-trip from sensor reading to dashboard update completes in under 2.5 seconds, the broadcast interval configured in `broadcast_sensor_feed_loop(interval_seconds=2.5)` at `backend/main.py:30`.

Q2: What is the FastAPI backend architecture and how is it structured?
A: The backend runs FastAPI 0.141.x on Python 3.12 with Uvicorn, structured across three modules: `backend/app/schemas.py` (Pydantic data contracts), `backend/routers/rockfall.py` (all route handlers and WebSocket logic), and `backend/main.py` (app factory, lifespan, CORS, router mounting). The `POST /predict` endpoint accepts an optional `SensorReading` body and returns a `RiskPrediction` — currently mock-weighted 60/25/15 to match the real target class distribution. The `GET /` root returns service status and uptime; `GET /health` provides a lightweight liveness probe for Render deployment health checks. CORS is configured via the `FRONTEND_ORIGIN` environment variable with fallbacks to `localhost:3000` and `127.0.0.1:3000` for local development. The router is mounted both at root (`/predict`, `/ws/feed`) and under the `/api/rockfall` prefix for clean API namespacing without duplicate route definitions.

Q3: Why Next.js 16 with App Router, React 19, and TypeScript 5.9 — and not other frameworks?
A: Next.js 16.3.1 was chosen specifically for its App Router (file-based routing with React Server Components), Turbopack-native dev mode (scripted as `next dev --turbopack` in `package.json`), and first-class TypeScript support. React 19.2.8 brings concurrent rendering and automatic batching, which is critical when the WebSocket feed pushes telemetry updates every 2.5 seconds across multiple chart and map components simultaneously. TypeScript 5.9.3 was deliberately held back from TS7 because `eslint-config-next@16.3.1` is not yet compatible with TypeScript 7 — this was a conscious trade-off to keep the ESLint pipeline functional during the hackathon. Tailwind CSS 4.x is used for utility-first styling with the `@tailwindcss/postcss` plugin. The combination yields sub-second hot-reload during development via Turbopack and production-ready SSR on Vercel without additional build tooling.

Q4: How does the 3D pit visualization work with MapLibre GL?
A: MapLibre GL JS v6.4.1 renders the Kusmunda mine pit as a 3D terrain heatmap using the open-source MapLibre GL spec (BSD-3 license). React-Map-GL v8.1.2 provides the React wrapper (`react-map-gl`), enabling declarative map component composition inside Next.js. The zone grid from `data/zone_grid.json` defines 16 GeoJSON Polygon zones with centroids, bounding boxes, and full coordinate rings — each zone is rendered as a fill layer with color mapped to the real-time `risk_score` (0–1) from the WebSocket feed. The `PitHeatmap` component (exported from `frontend/components/map/index.ts`) handles zone geometry overlay, 3D pitch/tilt for pit depth perception, and dynamic color interpolation. Critically, MapLibre requires no API key and no token — it was selected over Mapbox GL specifically to avoid a paid dependency during the hackathon. The terrain tiles load from MapLibre's open tile servers, and the 3D extrusion is computed client-side without any server-side rendering cost.

Q5: How are the Pydantic data contracts designed and enforced?
A: Three Pydantic `BaseModel` classes in `backend/app/schemas.py` define the entire data contract: `SensorReading` (sensor_id, zone_id, timestamp, displacement_mm_day, vibration, pore_pressure, strain, rainfall_mm), `RiskPrediction` (zone_id, timestamp, risk_level as `RiskLevel` enum, risk_score bounded 0–1 via `Field(ge=0.0, le=1.0)`, displacement_velocity_mm_day, model_version), and `AlertEvent` (alert_id, zone_id, severity, message, triggered_at, acknowledged). The `RiskLevel` enum constrains values to exactly `"safe"`, `"warning"`, or `"evacuation"` — impossible to produce an invalid risk level at runtime. The `risk_score` field uses Pydantic's `Field` validation to reject any value outside [0.0, 1.0]. Frontend types in `frontend/lib/types.ts` are hand-mirrored from the backend schemas with identical field names and snake_case casing — the file header explicitly states "Hand-mirrored from backend/app/schemas.py for zero-translation-risk." This dual enforcement means the backend validates at write-time via Pydantic, and the frontend validates at read-time via TypeScript interfaces, with zero field name mismatches between the two layers.

Q6: How does the mock-to-real model swap work with zero frontend changes?
A: The `POST /predict` endpoint at `backend/routers/rockfall.py:158` accepts a `SensorReading` and returns a `RiskPrediction` with `model_version="v1.0.0-mock-xgb"`. The mock generator uses weighted random selection (60% Safe, 25% Warning, 15% Evacuation) with displacement ranges hardcoded to the SSR thresholds (0–50, 50–120, >120 mm/day). To swap in the real XGBoost model, only the function body of `predict_rockfall()` needs to change — the Pydantic input/output schemas remain identical. The WebSocket broadcast loop (`broadcast_sensor_feed_loop`) already uses the same `generate_mock_reading_and_prediction()` function and emits the exact same JSON payload shape that the frontend `SensorWebSocketClient` expects. Because the `RiskPrediction` schema is frozen (defined in `backend/app/schemas.py` and mirrored in `frontend/lib/types.ts`), the swap is a single function-level replacement inside `rockfall.py` — no frontend component, WebSocket handler, or chart reconfiguration is needed. This is by design: the Day 0 frozen data contract guarantees that model version changes never break the presentation layer.

Q7: What is the ConnectionManager broadcast pattern and why is it used?
A: The `ConnectionManager` class at `backend/routers/rockfall.py:32` maintains a `set[WebSocket]` of all active connections. On each WebSocket accept, the connection is added to the set; on disconnect or send failure, it is discarded. The `broadcast()` method iterates over all active connections, serializes the payload via `json.dumps()`, and sends to each — dead connections that throw exceptions during `send_text()` are collected in a `disconnected` set and removed after the iteration completes. This pattern avoids the need for a message queue or pub/sub broker because the system is single-process (FastAPI + Uvicorn on Render). The background task `broadcast_sensor_feed_loop(interval_seconds=2.5)` runs as an `asyncio.create_task` inside the FastAPI lifespan context manager, generating a new `(RiskPrediction, SensorReading)` pair every 2.5 seconds and broadcasting the combined `telemetry_update` payload to all connected clients. The lifespan shutdown gracefully cancels the broadcast task via `broadcast_task.cancel()` and catches `CancelledError`, preventing orphaned background work when the server restarts.

Q8: What are the Turbopack and React 19 benefits for the dashboard?
A: Turbopack is invoked via `next dev --turbopack` in `package.json:7`, replacing Webpack as the dev bundler. Turbopack's incremental compilation means that only changed modules are re-bundled during development — for a dashboard with 8+ zone heatmap layers, Recharts trend components, and WebSocket state management, this reduces hot-reload latency from seconds to milliseconds. React 19.2.8's automatic batching ensures that multiple state updates from the WebSocket feed (sensor_reading, risk_prediction, timestamp) are batched into a single re-render cycle instead of triggering sequential re-renders per field. The `SensorWebSocketClient` in `frontend/lib/websocket.ts` uses a listener pattern (`onMessage` returning an unsubscribe function) that integrates cleanly with React 19's `useEffect` cleanup semantics, preventing memory leaks from stale WebSocket handlers when components unmount during route transitions between `/dashboard`, `/trends`, and `/alerts`.

Q9: How is the 4×4 zone grid designed and why 16 zones?
A: The 4×4 regular grid was generated by `scripts/phase4_sar.py:125` over the Kusmunda Mine AOI bounding box (lat 22.3204–22.3420, lon 82.6476–82.6882) and persisted to `data/zone_grid.json`. Each zone is a GeoJSON Polygon with a centroid, bounding box, and full coordinate ring — the grid spans approximately 2.4 km (N-S) × 4.2 km (E-W) with a diagonal of ~4.8 km. The 16-zone resolution was chosen to balance spatial granularity against data density: with 356 temporal acquisitions across 12 months, the synthetic training dataset contains 5,696 rows (16 zones × 356 days), which is sufficient for XGBoost/RF training while keeping the per-zone cell size (~600 m × 1,050 m) large enough that Sentinel-1's 10 m pixel resolution provides meaningful zonal statistics. The zone grid is the single source of truth shared by Phase 4 (SAR extraction), Phase 6 (zone feature assembly), Phase 7 (synthetic sensor generation), and the frontend PitHeatmap component — all reference the same `zone_grid.json` file.

Q10: How does the geospatial data pipeline work end-to-end?
A: The pipeline spans three scripts: `phase3_terrain.py` pulls Copernicus GLO-30 DEM from Google Earth Engine (`projects/sat-io/open-datasets/GLO-30`), clips it to the AOI bbox, and exports a 30 m resolution GeoTIFF. The DEM is loaded via `rasterio` into a `richdem.rdarray` with geotransform set to 30 m cell spacing (critical: the raw geographic coordinates in degrees would distort slope to ~90° without metric cell sizes). Three terrain derivatives are computed using `richdem.TerrainAttribute`: slope_degrees (Horn 1981, output range 0–90°), aspect (downslope azimuth 0–360°), and profile_curvature (Zevenbergen & Thorne 1987, negative = convex = high detachment risk). Each derivative is exported as a GeoTIFF with matching CRS (EPSG:4326) and transform, and a 2×2 matplotlib sanity-check plot is generated. The resulting slope.tif, aspect.tif, and curvature.tif are then zone-averaged in Phase 6 to produce per-zone terrain features that join the 10-feature ML vector.

Q11: How is Sentinel-1 SAR backscatter processed?
A: `phase4_sar.py` queries the Sentinel-1 GRD collection (`COPERNICUS/S1_GRD`) from GEE, filtered to the Kusmunda AOI, IW mode, dual VV/VH polarization, and the 12-month window from 2025-08-19 to 2026-08-19. The pipeline evaluates ASCENDING vs DESCENDING orbit passes and selects DESCENDING Track 19 (or whichever dominant track provides 100% AOI spatial containment without edge clipping) — this locks the incidence angle across all 30 acquisitions to prevent radiometric calibration drift. Server-side `reduceRegions` with `ee.Reducer.mean()` computes zonal mean VV and VH backscatter (in dB, sigma nought) for each of the 16 zones across all acquisitions, producing `data/sar_backscatter.csv` with schema [date, zone_id, VV_mean, VH_mean]. The sanity check verifies dB values fall within the expected -25 to 0 dB range for land surfaces. Importantly, this is amplitude backscatter change detection, not InSAR — the VV signal tracks surface roughness and moisture dynamics, while VH tracks volume scattering and structural disaggregation, both serving as physical proxy signals for surface disturbance preceding failure.

Q12: How is Open-Meteo rainfall integrated and why is no API key needed?
A: `phase5_rainfall.py` queries the Open-Meteo Historical Archive API (`archive-api.open-meteo.com/v1/archive`) using a simple HTTP GET request with parameters: latitude=22.3312, longitude=82.6679 (the locked AOI center from `data/aoi.json`), daily=precipitation_sum, timezone=UTC, and date bounds extracted from the SAR temporal range (2025-08-22 to 2026-08-12). The API is unauthenticated — no API key, no OAuth, no rate limit tokens — because Open-Meteo serves ERA5 and ERA5-Land reanalysis data as an open-access public good. The script validates that all 356 continuous days are returned with zero null values and zero negative precipitation, then exports `data/rainfall.csv` with schema [date, rainfall_mm]. A key architectural insight documented in the script: the ERA5-Land reanalysis grid resolution is ~0.1° (~9–11 km), while the entire Kusmunda pit spans only ~2.4 × 4.2 km — meaning all 16 zone centroids fall within a single atmospheric grid cell and return numerically identical precipitation series. A single AOI-center query therefore captures the exact rainfall for the entire mine, eliminating redundant API calls.

Q13: Why MapLibre GL instead of Mapbox GL?
A: Mapbox GL JS requires a valid access token for all map tile requests, and its free tier is limited to 50,000 map loads per month — a constraint that could be exceeded during hackathon development iterations alone. MapLibre GL JS v6.4.1 is the fully open-source fork (BSD-3 license) of the original Mapbox GL spec, with identical rendering capabilities, 3D terrain support, and vector tile protocol. The critical difference: MapLibre loads terrain tiles from open tile servers without any token or API key, making it zero-cost and zero-dependency for a hackathon submission where budget and key management are unsorted risks. The `react-map-gl` v8.1.2 wrapper provides the same React-idiomatic API that Mapbox GL would, so the `PitHeatmap` component code is structurally identical to what a Mapbox implementation would look like — but with no `.env` variable, no token leak risk, and no vendor lock-in. For a system targeting cost-constrained Indian mines, choosing an open-source mapping stack also aligns architecturally with the project's core thesis of replacing expensive proprietary monitoring (SSR at ₹2–4 crore/unit) with affordable alternatives.

Q14: How is the schema contract enforced between frontend and backend?
A: The enforcement is manual but disciplined: `backend/app/schemas.py` is the single source of truth, and `frontend/lib/types.ts` is explicitly documented as "Hand-mirrored from backend/app/schemas.py for zero-translation-risk." Field names (snake_case), types (string, number, enum), and shapes (nested objects, optional fields) match exactly between the two files. The backend enforces contracts at runtime via Pydantic's `BaseModel` validation — any request with a missing `sensor_id`, a `risk_score` outside [0.0, 1.0], or an invalid `RiskLevel` enum value is rejected with a 422 Unprocessable Entity before it reaches any business logic. The frontend enforces contracts at compile-time via TypeScript interfaces — the `SensorWebSocketClient<T>` generic type parameter means the WebSocket message handler receives typed data, and any field name mismatch would produce a TypeScript compilation error. The displacement velocity thresholds are also duplicated as constants in both files: `SAFE_DISPLACEMENT_MAX_MM_DAY = 50.0`, `WARNING_DISPLACEMENT_MIN_MM_DAY = 50.0`, `WARNING_DISPLACEMENT_MAX_MM_DAY = 120.0`, `EVACUATION_DISPLACEMENT_MIN_MM_DAY = 120.0` — identical values in `backend/app/schemas.py:18-21` and `frontend/lib/types.ts:42-45`.

Q15: Why WebSocket over polling for real-time telemetry?
A: The WebSocket `/ws/feed` endpoint maintains a persistent bidirectional connection between the FastAPI backend and the Next.js dashboard. The `broadcast_sensor_feed_loop` pushes a `telemetry_update` payload every 2.5 seconds to all connected clients without the client ever requesting data — this is push-based, not pull-based. HTTP polling at the same frequency would require a new TCP handshake, HTTP request headers, and TLS negotiation every 2.5 seconds per client, adding 100–300 ms of latency per round trip and consuming unnecessary bandwidth on both the Render backend and the client. WebSocket eliminates this overhead: after the initial upgrade handshake (a single HTTP 101 Switching Protocols), all subsequent messages are binary frames with ~2–5 bytes of overhead versus ~800 bytes for a full HTTP request. The `SensorWebSocketClient` in `frontend/lib/websocket.ts` also implements automatic reconnection with a configurable 3-second backoff (`reconnectIntervalMs = 3000`), connection status tracking (`connecting | open | closed | error`), and a listener pattern that integrates with React's useEffect cleanup — so when the browser tab loses focus or the network drops briefly, the client reconnects and resumes receiving telemetry without manual intervention. For a safety-critical alerting system where seconds matter, the sub-100 ms push latency of WebSocket versus the 100–300 ms round-trip of polling is a material difference.
