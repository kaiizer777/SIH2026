Pitch File 06 — Defense Questions (What Judges Will Ask)

Q1: "What if your model just predicts safe always?"
A: A model that always predicts 'safe' scores ~60% accuracy and is worthless — it never catches a real evacuation event. That's why we don't report accuracy as our headline metric. We report precision and recall on the evacuation class specifically, using class-weighted training so loss penalizes missing evacuation far more than misclassifying safe. Missed evacuation equals life-safety failure; false alarm equals inconvenience. Our XGBoost achieves 100% evacuation recall and 97.04% precision on 197 test-set evacuation events, proving the model actively learns evacuation signatures rather than defaulting to the majority class.

Q2: "Your data is synthetic — how is this real?"
A: Sensor data is synthetic — this is deliberate and defensible, since we had no live mine access during the hackathon. However, DEM data comes from Copernicus GLO-30, SAR backscatter from Sentinel-1 GRD, and rainfall from Open-Meteo ERA5 — all real, publicly available geospatial datasets. We calibrated synthetic magnitudes against Landslide4Sense, NASA GLC, and Dorren et al. to ensure realistic ranges. The synthetic data follows Fukuzono (1985) physics for rainfall-infiltration coupling, not arbitrary random generation.

Q3: "You claimed InSAR — that's not what you're using."
A: Corrected proactively: Sentinel-1 GRD provides amplitude backscatter, NOT phase-based interferometry. We do NOT claim mm-precision deformation measurement. Backscatter change detection is a real, defensible proxy signal for surface disturbance — moisture changes and roughness variations preceding slope failure alter radar return intensity. This distinction is stated in all project documentation. We chose GRD over SLC because GRD is terrain-corrected and analysis-ready without requiring Phase-Based processing pipelines.

Q4: "Why not use real sensor data?"
A: No live mine access was available during the hackathon timeline. Synthetic data is the honest, defensible approach rather than fabricating field access we did not have. Real geospatial data — DEM, SAR, and rainfall — IS used for terrain and environmental context. The pipeline is designed so swapping synthetic for real sensors requires zero schema changes: same SensorReading contract, same feature pipeline, same model input format. A mining company deploying this would feed real sensor streams directly into the existing architecture.

Q5: "How do you handle class imbalance?"
A: We use class-weighted loss via compute_sample_weight('balanced', y_train) in scikit-learn. We specifically chose NOT to use SMOTE because sensor channels are physically correlated — displacement, vibration, pore_pressure, and strain co-vary per the Fukuzono curve. Synthetic interpolation via SMOTE risks generating physically implausible readings that violate these coupling relationships. Weighting keeps every training point physically real while forcing the model to treat the minority evacuation class as critical. This directly contributes to our 100% evacuation recall on XGBoost.

Q6: "Why temporal split instead of random?"
A: Random split causes temporal leakage: day 200 of zone_07 in training, day 199 in test — the model sees an adjacent precursor trajectory and trivially predicts it. Our temporal split uses a cutoff date of 2026-06-03, matching the deployment scenario where the model must generalize forward in time on the same mine. This is NOT GroupKFold on zone_id — GroupKFold tests unseen zones, which is a different question about spatial generalization. Temporal splitting ensures the model proves it can catch events it has never seen before in the timeline.

Q7: "Is 97.98% accuracy good enough?"
A: Accuracy is NOT our headline metric. On a dataset with 61% safe, 26% warning, and 13% evacuation distribution, a model that "always predicts safe" gets ~60% accuracy and is completely worthless — it never catches a real event. We report evacuation-class recall specifically: XGBoost achieves 100% and Random Forest achieves 98.48%. We also report evacuation precision: XGBoost at 97.04% and RF at 99.49%. The 100% recall means zero missed evacuations on 197 test-set evacuation events for XGBoost.

Q8: "What about false alarms?"
A: False alarm rate matters but is asymmetric with missed evacuations. XGBoost evacuation precision is 97.04%, meaning 2.96% of evacuation alerts are false alarms — an inconvenience that triggers unnecessary response. A missed evacuation, however, is a fatality. Our metric choice reflects this fundamental asymmetry: we optimize for recall (catch every real event) while monitoring precision to keep false alarms manageable. In practice, even a 3% false alarm rate is acceptable compared to industry alternatives where single-modality radar systems also produce false triggers.

Q9: "Why SHAP and what does it prove?"
A: SHAP using TreeExplainer with model_output='raw' proves the models learn beyond simple displacement thresholds. In v1 (displacement-only labels), XGBoost showed 0.00% terrain and SAR contribution — the model had no reason to use those features. In v2 (terrain-modulated labels), XGBoost jumped to 6.75% and RF to 18.63% terrain contribution. The before/after delta is the key evidence: geospatial features are causally encoded in the labels and genuinely learned by the model, not spurious correlations. Without SHAP, we could not distinguish real feature learning from coincidental correlation.

Q10: "What's the RF 30.31% terrain artifact?"
A: Random Forest's terrain contribution is stable at 30.31% regardless of multiplier strength, confirmed via v2b and v2c isolation tests where we varied the terrain modulation factor. This stability proves the contribution is driven by spatial autocorrelation — slope angle correlates with zone tier, so RF uses terrain as a zone-identity proxy. It is NOT a signal we can claim credit for as a genuinely learned physical relationship. We transparently report this in the feature importance analysis rather than inflating the RF terrain numbers.

Q11: "How does this compare to SSR?"
A: Slope Stability Radar is the gold standard — sub-millimeter precision, $250,000 to $500,000 per unit, line-of-sight only. Our system is explicitly not a replacement; it is a complement extending coverage to peripheral benches and smaller mines where full SSR deployment is not economically viable. We fuse 10 modalities — displacement, vibration, pore pressure, strain, temperature, humidity, rainfall, DEM slope, SAR backscatter, and vegetation index — versus SSR's single displacement measurement. This multi-modal fusion provides contextual awareness that single-sensor systems cannot achieve at any price point.

Q12: "What's the alert lead time?"
A: Our target is sub-minute latency from sensor reading to dashboard alert via WebSocket push to the React frontend. Reference architecture from an IEEE paper addressing the same SIH problem reports approximately 30-minute mean lead time with a hybrid CNN-LSTM model. Our XGBoost achieves 100% evacuation recall on the test set, meaning it catches every precursor event when one occurs. The real bottleneck is not model inference but sensor data transmission, which depends on mine infrastructure — our edge architecture addresses this directly.

Q13: "Can this work offline at a remote mine?"
A: The edge architecture runs sensors to Raspberry Pi or Jetson, performs ONNX Runtime inference locally, and triggers sirens, GPIO, or GSM SMS alerts with zero internet requirement. Cloud dashboard synchronization happens opportunistically when connectivity returns. We chose ONNX over TensorFlow Lite because ONNX is faster on ARM CPU hardware and provides one format that covers XGBoost, GRU, and CNN-LSTM models. A remote mine in Jharkhand with no broadband still gets real-time local alerting — the cloud layer is for analytics and compliance reporting, not safety-critical functions.

Q14: "Why not LSTM/GRU first?"
A: Model progression follows literature consensus: Random Forest and XGBoost baseline first to establish the evaluation framework and feature importance methodology, then LSTM and GRU for time-series pattern capture, then hybrid and ensemble methods like CNN-LSTM. The comparison table is a running asset — the GRU column is marked TBD in our current results. Critically, XGBoost already achieves 100% evacuation recall, setting a high bar that any GRU variant must match or exceed to justify its additional complexity and inference cost.

Q15: "What's the cost of inaction?"
A: Major slope failure events cost ₹500 crore or more per incident, estimated from published industry data on Indian mining disasters. Beyond direct financial loss, failures cause worker fatalities, regulatory shutdowns by DGMS, environmental contamination, and community displacement. DGMS — the Directorate General of Mines Safety — mandates slope monitoring for mines above specified thresholds. Our system enables compliance for the hundreds of Indian mines that cannot afford SSR at ₹2 crore per unit, making safety monitoring economically accessible where it previously was not.
